## Architecture

**Resonance**（共振）is a multilingual social storytelling platform built around "story cards" — users write cards, respond to others by authoring a *resonance* (a response card with a `referenceCardId`, **not** a like), and form one-to-one connections by resonating, or when a card's author replies to a note (older invites can still be answered, none are sent). Built with Next.js 15 (App Router) + React 19 + TypeScript 5.7 (strict). No Tailwind — all styling uses CSS Modules + CSS custom properties defined in `src/styles/tokens.css`. `README.md` is the project's landing page (what, why, download, getting started; `README.zh-TW.md` in Chinese) and `CONTRIBUTING.md` / `SECURITY.md` say how to help and how to report a vulnerability; the older architecture write-up in Chinese is `docs/ARCHITECTURE.zh-TW.md` (this file is the current one).

Stack: Firebase Auth + session cookies, Cloud Firestore, Cloudflare R2 (object storage), OpenAI (slugs/tags/illustrations), Tiptap 3 editor + react-markdown reader, SWR for client data fetching. Deployed on Vercel at https://resonance.channel (www redirects to it): functions in `hkg1` (nearest Firestore's asia-east1), except the routes that call OpenAI — which refuses requests from Hong Kong — pinned to `hnd1` in vercel.json `functions` (see AI). The old address, resonance-world.vercel.app, serves the same deployment; vercel.json `redirects` sends its pages (path and query) to resonance.channel with a 308, but not `/api/*`, `/_next/*` or `/.well-known/*`, which keep answering there for app builds already installed and Android's App Links — `src/lib/site.test.ts` pins that, so don't widen it.

### Routing & i18n

`src/middleware.ts` intercepts all requests and routes through `[locale]` (supports `en` and `zh-TW`, `localePrefix: 'always'`). The `next-intl` plugin handles server-side translations; message files live in `src/messages/{locale}.json`. The path alias `@/*` maps to `src/*`. Note: `next.config.ts` lists `firebase`/`firebase-admin` in `serverExternalPackages` to avoid Webpack vendor-chunk require errors.

**Copy**: a string of one sentence or a fragment ends without a full stop in both languages (zh-TW no 「。」, en no "." — titles, labels, buttons, placeholders, hints, captions, empty states, status lines, toasts, inline errors, push copy); two or more sentences keep every stop, the last too; ？！… stay; en alone keeps the period on a one-sentence alert/confirm dialog body (Apple style; listed in `src/messages/punctuation.test.ts`, which guards the rule).

App routes under `src/app/[locale]/`:

- `page.tsx` — marketing landing page (`SiteHeader → HeroSection → CardFeedSection → CTASection → SiteFooter`)
- `(auth)/` — `signin`, `signup`
- `(app)/` — `home` (feed), `me`, `settings`, `messages` (DMs), `write/[id]` (editor), `card/[slug]` (card page: ISR, `revalidate = 300`, and `next.config.ts`'s `expireTime: 86400` bounds any stale ISR HTML to a day; a server component seeds `CardDetailClient` through `src/lib/data/cardSeed.ts` — a public card's story is in the HTML, an anonymous card's author never is — and the client replaces it with its own read through the rules; blocks stay client-side, `cardHold.ts` hides the card pre-paint in a signed-in browser until the block list is known), `u/[handle]` (public profile)

Outside `[locale]`, at the root: `robots.ts` (on the production deployment only — `VERCEL_ENV`; previews and local builds disallow everything — it opens the public pages, closes `/api/` except `/api/og/` and the signed-in app's pages, and names the sitemap) and `sitemap.ts` (the landing and policy pages in both locales with hreflang, and the newest `SITEMAP_MAX_CARDS` public, published, non-anonymous cards by slug, read with the Admin SDK; ISR hourly, and `revalidateLocalized` drops it whenever the landing page is among the paths). Lists in `src/lib/seo.ts`. A root file with neither a metadata route nor a `public/` file falls into `[locale]` and 404s — as /robots.txt and /favicon.ico once did. Also there: `download/route.ts` — /download, the link the landing page's QR code (`public/download-qr.svg`, made once by `scripts/web/download-qr.swift`) encodes: an iPhone/iPad goes to the App Store, Android to Google Play, anything else to the landing page's `#download` block (store links and the UA rule in `src/lib/appStores.ts`); the middleware's matcher skips exactly that path. The download badges are `molecules/GetTheApp` (Apple's and Google's official files in `public/badges/`, never modified — a test pins their hashes — drawn at one visible height): the server renders both stores, a phone keeps its own after hydration, and only a hover-and-mouse device sees the QR code. Every page carries Safari's Smart App Banner (`itunes` in the locale layout's metadata).

### Authentication

1. Browser signs in with the Firebase client SDK (Google / Email; phone OTP behind `NEXT_PUBLIC_ENABLE_PHONE_OTP`) and gets an ID token.
2. `POST /api/auth/session` exchanges it for an httpOnly session cookie (`__session`, signed by firebase-admin); it takes JSON from the site's own origin only (login CSRF), and a bad token is a 401. `DELETE` logs out. The browser mints it in the background (`ensureSession()` in `src/lib/auth/firebase/client.ts`: deduped, only when missing or under a day from expiry, remembered in localStorage `resonance:session`); explicit sign-ins await it. `useAuth().loading` ends as soon as the SDK restores the user; only callers of cookie-authenticated `/api` routes wait for `useAuth().sessionReady` — prefer `callApi` (Bearer) for new calls. The sign-in pages keep the popup resolver (Safari blocks the popup otherwise).
3. Server code verifies the cookie or ID token via `getCurrentUser()` in `src/lib/auth`, locally (signed out is a 401 everywhere, never a 500). Revocation and disabled state are asked of Firebase Auth live on writes, `/api/account/*`, upload and generate-image; v1 GETs and `/api/recommend/feed` use a per-instance cache (`REVOCATION_CACHE_MS`, 2 min) via `getCurrentUser({ revocation: 'cached' })`. Revoke with `revokeSessions(uid)` (clears the local entry), never a bare `revokeRefreshTokens`. An Auth outage is `AuthUnavailableError` → 500, never a 401.
4. Firestore waits for Auth restoration on its own, so public reads (feed, related, resonances) don't gate on auth; reads of the viewer's own data wait for the user.

### Data Layer (dual-track Firestore)

- **Server side**: `src/lib/db/firestore/*.ts` — repository classes (`FirestoreCardRepository`, `FirestoreUserRepository`, plus connection/notification) using the admin SDK, enforcing visibility (`public` / `connections` / `private`) in code. Connections use a sorted `uid1_uid2` pair id.
- **Client side**: `src/lib/db/firestore/client/*` — direct read/write modules (cards, feed reads, invites, notifications, profile) consumed by SWR hooks in `src/lib/data/hooks.ts`; security is enforced by `firebase/firestore.rules`. Writes that reach another person or must be unique — publishing, pen names, messages, notes, resonating with a card already written — go through `/api/v1` like the apps (`callApi` in `client/api.ts` sends the ID token as a Bearer token), and the rules refuse them from the browser. Saving an edit to a published card goes through it too: the editor autosaves into `cards/{id}/edits/current` and the server applies that (`POST …/edits/apply`; the rules still let the author write the card, for older app builds). What stays client-direct is the author's own drafts and settings, reads, and a few narrowly checked legacy paths. The repo and web config are public: a rule is the only guard on a client write, so every new one needs field-level checks (key whitelist, types, sizes — the same limits the server applies when it copies content, `cardContent.ts`) and a `test/emulator/rules.emulator.test.ts` case. A card read failing for any reason but permission-denied / not-found (`isAbsent()` in `client/errors.ts`) throws rather than reading as "no such card", so SWR retries.
- **Anonymity**: an anonymous card's document names its author, so the rules let only the author read or list it; every public client list must say `where('anonymous', '==', false)` (composite indexes exist for each). Everyone else gets an anonymous card from the server, which leaves the author out: signed in through `/api/v1`, signed out through `GET /api/cards/view` (the card page falls back to it) and `GET /api/cards/latest` (the home feed). Card links are server-only; a link into someone's anonymous card shows on their profile only to them. Notes are readable by their recipient only; a note on a named card is also a message in the two people's conversation (below), one on an anonymous card never is — not even between two people already connected — and never opens, counts toward or answers a letter (Safety). A block never hides an anonymous card nor refuses what is aimed at one (Safety). An anonymous card is public or private, never for connections only (Safety). Publish always writes a boolean `anonymous`.
- **Browser SDK**: client modules use Firestore Lite through `src/lib/db/firestore/client/sdk.ts` (writes land in call order; reads wait for this browser's writes in flight) — import from `./sdk`, never `firebase/firestore` (sdk.test.ts fails otherwise). The only realtime surface is `client/realtime.ts` (full SDK), reached through `listenLazily` (`client/listen.ts`) — an open thread, and the header's badges (`lib/data/live.ts`: one listener per key, shared, lingering 60 s after its last reader: the newest 50 conversations, the newest 20 bells); the two SDKs' Timestamps are different classes, so map listener data by shape. The landing and policy pages load no Firestore for a signed-out visitor; modals and the thought map's editor load on first open (next/dynamic).
- **An open thread** (`useChatThread` in `lib/data/thread.ts`; its pure pieces in `src/lib/chat`, twins of the apps' kit/chat): the newest 50 messages live, older pages read through Lite before the oldest held (`getOlderMessages`: a cursor of the send time to the microsecond plus the id — never a Date, which would skip messages), a search reading the whole history (≤ 5000). The viewer's sends go through the conversation's outbox (`outboxOf`, kept for the page's life): drawn at once, sent in order under a `clientId` the server makes the document id (the row keeps it as its key), a passing failure stops the line, a refusal fails only its message.
- **Signed-in pages read through `/api/v1`**, one request each: the card page's surroundings (`useCardPageLists`: `GET /cards/{id}?include=resonances,related,links,embeds`), a profile (`useProfilePage`: `GET /users/{handle}?include=cards,links`), a thread's cards — shared ones and Resonance card links (`useCardSummaries`: `GET /cards?keys=`, 30 per request, each card asked for once; the answer names the cards it covers, `asked`, and the ones whose request failed, `failed`, which their embeds read themselves). Signed-out readers stay on Firestore through the rules, except the home feed and anonymous cards (above); `useReadPath()` picks ('v1' / 'public' / null while auth restores). API summaries become list Cards through `lib/data/summaries.ts` (marked `summary`, never used to prefill a card page); story embeds find their card in `CardEmbedSourceContext` when the page provides one. The card ⋯ (`CardActionsMenu`) changes visibility and deletes through `PATCH`/`DELETE /api/v1/cards/{id}`, which revalidate on the server.
- **SWR defaults** live in `SWRProvider` (`SWR_DEFAULTS`: no focus revalidation, 30 s dedupe); hooks opt back in with `LIVE_ON_FOCUS` (conversations, block list) or keep a short window with `OWN_CONTENT` (anything the viewer edits). Profiles go through one page-wide cache (`getUsersByIds` in `client/reads.ts`: `documentId() in` batches of 30, 5-min TTL; `forgetCachedUser(uid)` after writing a profile). Never batch-read cards with `in` — the rules refuse the whole query when one card is unreadable. List clicks seed the card page's cache (`cardKey()` / `usePrefillCard()` in `src/lib/data/cardPrefill.ts`). The card page's 共振 opens `ResonatePicker` (write a new card, or pick a published public card of yours answering nothing: `resonateChoices`; a tap marks it, 共振 sends it), and the owner's ⋯ takes a resonance back (取消共振); both then re-read what shows the link through `useResonanceRefresh()` (`src/lib/data/resonate.ts`): the original's button, both cards' pages, the published and resonated shelves, the thought map. A published resonance turns the button into 已共振, which opens it; a draft one stays 修改. The card box reads the shelf on screen only (`useMyCardBox(shelf)`, key `cardbox:{uid}:{shelf}`): the viewer's own shelves through the rules, others' cards (resonated, linked, bookmarks) from `GET /api/v1/me/cards?tab=`. `getMyBlockedIds` waits for Auth to restore the viewer and is read beside each list's cards. `useMediaQuery` is null until hydrated.

Core entities live in `src/lib/db/types.ts`: `Card` (with `translations`, `tags`, `slug`, counters), `User` (`handle`/`handleLower`), `Connection`, `Invite`, `Resonance`, `CardLink`, `Notification`. `src/lib/adapters/` converts Firestore data to UI models.

After editing `firebase/firestore.rules` or `firebase/firestore.indexes.json`, deploy from the `firebase/` directory (that's where `firebase.json` lives — the command fails at repo root): `cd firebase && firebase deploy --only firestore:rules,firestore:indexes`.

A draft set to be anonymous and for connections only is 400 (Safety) |
| `POST /api/v1/cards/{id}/resonances` `{ cardId }` · `DELETE …/resonances/{cardId}` | resonate with a card using one you've already written (`resonate.ts`): your published **public** card gets `referenceCardId` = this card — the field every resonance list already reads, so nothing else is stored — without touching `updatedAt`; answers `{ card, changed }` (a repeat is `changed: false`). A card answers one card and a reader answers a card with one of theirs: a card already answering another, or a second card of yours for this one (a draft resonance too; the read is in the transaction, so racing taps can't both win), is 409 `conflict`; your own card, or one answering yours (a 2-cycle), is `invalid_request`; a block either way is `blocked` on a named card (an anonymous one is answered all the same and reaches no one). Reaches the original in the pointing's own transaction, as every resonance path does (`readReach` + `reachOriginal`, see Safety): connection unless either card is anonymous, one bell per reader per card (`notifications/resonance_{uid}_{cardId}`, so undo-and-pick-again rings once), none from an anonymous card; no pen name is 403 `forbidden` ('Choose a pen name first.', as for a note, asked before the blocks) when your card is public under your name — an anonymous one reaches no one and needs none; bucket `resonate`; your card's pages revalidated after the response. DELETE clears the field (`FieldValue.delete()`) on your card, written resonances too; idempotent 204; it takes the resonance back as a reason the two are connected, and the connection with it when nothing else holds it (Safety), and the bell stays |
| `GET /api/v1/users/{handle}` (+ `/cards`, `/links`; or `?include=cards,links&limit=`) | a profile as the viewer sees it, their public cards, cards linking to theirs. The cards' query itself asks `anonymous == false` (and `publishedAt != null`), as the web's does: a page ends at the last document the query gave (`pageEnd`), so a page token, a cursor or `cardCount` taken over an anonymous card would name it as theirs |
| `POST /api/v1/cards/{id}/edits/apply` | save changes to a published card (web and apps): its pending edit (`cards/{id}/edits/current`) becomes the card in one transaction, keeping its date and slug; after the response its link previews follow the new story, then pages and index are refreshed; an edit that makes a resonance public and named reaches its original as PATCH does (after the response); one that would leave the card anonymous and for connections only is 400, unless the card already is and the edit keeps both (Safety) |
| `POST /api/v1/notes` · `POST /api/v1/messages` | a note to a card's author (the server finds the author): on a named card it lands, in the same transaction, in their conversation (opened if need be) as `conversations/{pair}/messages/{noteId}` = `{ senderId, text, sentAt, cardRef: cardId, kind: 'note' }` — the note's own id, no `noteRef`, one more unread for the author, its bell row written already `pushedAt` (the chat push is the one buzz, no unfurl); on an anonymous card nothing but the note and its bell row, rung with `ringAfter`. Clients draw `kind: 'note'` as the author's card quoted above the note's words and ignore a `kind` they don't know. A note connects no one: between two people not connected it is a letter — the conversation's `request` = `{ from, cardId, at, count }` (the writer; their latest note's card and time; how many wait), at most `NOTE_REQUEST_MAX` = 3 counted in server-only `letters/{writer}_{author}` (Safety), then 409 `conflict` 'Wait for them to reply.' (nothing written or rung) — and a note to someone whose own letter to you waits answers it (connects you, deletes `request` and both counts) · a message to a connection (opens the conversation), or the answer to a letter (`request.from` = the recipient): it makes the connection and deletes `request` in its own transaction, and needs no new bell (the conversation exists); anyone else — the letter's writer too — is 403 'You can message people you are connected with.'. A message may carry `replyTo` (a message of the same conversation: kept as a `replyTo: { id, senderId, text ≤ 140, cardRef? }` snapshot, so the quote survives without reading the original) and `clientId` (16–64 of `[A-Za-z0-9_-]`; becomes the message's id, so a retry after a lost answer finds the message instead of sending it twice, and one that names someone else's message is refused). A note takes `clientId` too: it becomes the note's id (and its thread message's), and a resend is answered 201 with that id before the card or the blocks are asked — a withheld note's alike — writing, counting and ringing nothing, while the note exists (deleting the card deletes its notes: a resend after that is 404 like any note to a missing card); someone else's note, or a message already in the two people's thread on a named card, is 400 'Not a valid client id.'. Clients make one per send attempt and reuse it for every retry of that text. After the response every message rings the recipient (`pushMessage`) and its first link is unfurled (`unfurlMessage`). Both need the sender's pen name (`hasPenName`, else 403 'Choose a pen name first.'), asked before the blocks; a note reads its card's byline in its own transaction, and one on an anonymous card across a block is answered 201 and delivered to no one (Safety). A message's `noteRef` names a note its recipient left the sender, on that card — anything else (ids Firestore keeps for itself too) is 400 'That is not a note they left you.'; one left on the sender's anonymous card is quietly left off the message, which goes all the same (the thread would tell the note's writer whose card it was), and so is a note no longer there whose card is gone too (deleting a card deletes its notes) or isn't the sender's — the reply still answers a letter; a missing note on the sender's own card, still there, is the 400. A message (or a note in the thread) from the original's author of a resonance standing between the two, to its writer, answers that resonance — a reason they are connected for good (Safety) |
| `PUT/DELETE /api/v1/me/devices/{installationId}` | the apps' push registration: FCM token, UI language, `capabilities` (`chat-push` = the build draws a conversation's notification itself) and `timeZone` (an IANA name, kept when Intl knows it, else null — never a 400; not used for timing yet) in `devices/{installationId}` (no client rule; purged with the account) |

| `PATCH/DELETE /api/v1/cards/{id}` | the owner changes a card's visibility / anonymity, or deletes it (with its pending edit and vectors); both revalidate the cached pages. Hiding a published resonance (private, connections-only, anonymous — by PATCH or an applied edit) or deleting it takes it back in the same transaction, as DELETE …/resonances does (it is no longer a reason the two are connected; a hidden one still answers its original); the rules leave hiding one to the server (`publishedResonance`), and deleting any published card — a client deletes its drafts only (the web and both apps delete through this route; older tester builds that delete from the client are refused). **Push** (`src/lib/push`): every `notifications/*` row is also pushed to the recipient's devices through FCM (`pushNotification`: once-only via `pushedAt`, blocks re-checked, the bell's own `app.notifications.*` copy in each device's language, `data.route` a site path the apps open). Every bell row is written by the server, which rings it with `ringAfter()` after its response — or writes it already `pushedAt` when the chat push rings instead (a conversation's first message, a note in the thread) — and the rules refuse client creates of notifications and connections. Pushes that open a conversation carry `data.fromUserId`. A note or resonance bell on an anonymous card carries `payload.anonymous: true`, and its push routes to `/card/{cardId}`, without `fromUserId` — never the writer's thread, whose unread count they can watch drop as the card's author opens it. The bell lists read the flag too — the web's (`bellHref` in `AppHeader/bellLink.ts`, mirroring `pushRoute`) and both apps' `NotificationsScreen`: such a row opens the card, shows the note's words, offers no reply and marks no conversation read. An account keeps at most 20 devices (`MAX_DEVICES`); multicasts go 500 tokens at a time. What a push says comes from the records, not the row: the sender's current pen name and, for a note, the note's own text.

**Opt-in pushes** (both off until the person turns them on in settings — `notificationSettings/{uid}`, App Store 4.5.4 — and push only: never a bell row, since clients draw an unknown bell type badly; no `notificationId`; Android channel `picks` (`PICKS_CHANNEL`, named `native.channelNewCards`; builds without it fall back to `activity`), iOS `threadId: 'picks'`):
- *A card for tonight* (`push/picks.ts`, `/api/cron/push-picks`): per reader with `picks` on and a device — skipped when they asked for their picks themselves today (`recommendations/{uid}.askedOn`, written after the feed's response once a day — also when the request only waited on a build, a warm or failed one included — and by a build of theirs; a warm build doesn't set it), had one today (UTC) or three in the seven days ending today. The card is the first stored pick that isn't theirs, they didn't answer with a published resonance, wasn't pushed to them in 30 days, and is published and public now; a named card across a block either way is skipped, an anonymous one never for a block. Claimed in `pickPushes/{uid}` (`{ recent ≤ 30, sentAt }`) in a transaction before sending. Title `app.notifications.pickTitle`; body = the card's title (60 code points), then the stored reason on zh-TW devices or `pickBody` on others; never a pen name. `data: { type: 'pick', cardId, route: '/card/{slug||id}' }`, Android `tag: 'picks'` (tonight's replaces the last). The stored picks are read through `lib/recommend/stored.ts`, which reaches no LLM — keep it that way (`regions.test.ts`).
- *A new card from a connection* (`push/connectionCards.ts`, `announceNewCard` in the publish route's after-work, first publish only, once the slug has settled): a published, public, non-anonymous card by an author with a pen name (a resonance too, except to the author of the card it answers) goes to each connection with `connectionCards` on — not across a mute by the recipient or a block either way, not once the card (read again before each push) is no longer public, named and published. At most three a day per recipient, once per card (`connectionCardPushes/{uid}`: `{ day, cards }`, claimed in a transaction); the first 500 connections only (logged past that). Title `app.notifications.newCard` ({handle}), body the card's title, `data: { type: 'new_card', cardId, route }`.

**Chat push** (`push/chat.ts`, `pushMessage`, run with `after()` from `POST /api/v1/messages` beside the unfurl — each logs and gives up alone — and from `POST /api/v1/notes` for a note that went into the thread): every message rings, not only a conversation's first (whose bell row is written already `pushedAt`, so the chat push is the only buzz). It re-reads the message, stays silent across a block either way or when the recipient muted the connection (`connections/{pair}.muted` holds `{ by: recipientUid }`; a letter between two people not yet connected has none, and rings), takes the title from the sender's current pen name and the body from the stored text (140 code points, else the localized `app.notifications.messageCard`). A device registered with `chat-push` on Android gets a data-only high-priority message (`type: 'message'`, `conversationId, messageId, fromUserId, fromHandle, title, body, route, sentAt`) and draws a `MessagingStyle` notification of its own; every other device gets a plain notification push on the `messages` channel (`MESSAGES_CHANNEL`) with `tag`/`threadId` = the conversation, so a conversation replaces and groups its own. A note's message adds `kind: 'note'` to both kinds of push (the server only sends a kind it knows). A resent `clientId` pushes and unfurls nothing.

**Link previews** (`src/lib/links`; the server fetches an address a stranger wrote, so everything here is deny-by-default): `url.ts` is the one rule for what counts as a link — `firstLink`/`findLinks`/`normalizeLink`: http(s) only, no userinfo or `@`, port none/80/443, a host with a dot and ASCII (IDNs only as punycode), ≤ 2048 characters, trailing sentence punctuation (CJK too) and unbalanced `)` trimmed — written to be mirrored word for word by the web `linkify`, the Android `Linkify` and the iOS one. `unfurlMessage` (after the response, ≤ 8 s) takes the message's first link, fetches it with `safeFetch` and writes `preview: { url, title, description?, siteName?, image? }` onto the message, where the live listener delivers it (a client renders a message without it and again when it arrives); the result is remembered per instance (`memo.ts`), so a link sent over and over is fetched once. `safeFetch` resolves the name itself and refuses the fetch if ANY address is not public (`ip.ts`: IPv4 special-purpose blocks, IPv6 outside global unicast and its carve-outs, mapped forms judged by the IPv4 inside), connects to the vetted address through a pinned `lookup` (DNS rebinding), follows at most 3 redirects by hand re-vetting each hop, sends no cookie, Referer or credential (so a link to our own `/api` carries no session), has one 5 s deadline, reads a page to `</head>`/512 KB (a gzip bomb only that far), a JSON answer to 64 KB and an image to 5 MB (either refused past it), and takes `text/html` pages, `application/json` (mode `json`) and non-SVG `image/*`. A YouTube video (`oembed.ts`: youtube.com, www./m./music. and youtu.be, an 11-character id at /watch?v=, /shorts/, /live/, /embed/, /v/ or youtu.be/ — its page's head is over 512 KB of script before any title) is previewed from YouTube's oEmbed endpoint instead, in JSON mode, through a request built from the id alone: its title and channel (as the description) through `cleanText`, site name `YouTube`, the thumbnail only from i.ytimg.com (else `/vi/{id}/hqdefault.jpg`) through the signed proxy; a private or removed video (401/404) has no card. `openGraph.ts` reads the head tolerantly (comments, scripts and unterminated tags cannot hide or multiply tags) and treats every string as data: entities decoded once, tags, control, zero-width and direction-override characters removed, title ≤ 160, description ≤ 300, site name ≤ 80. The picture never goes to clients from the page's site: `imageProxy.ts` signs the `og:image` URL (HMAC-SHA256; key `LINK_PREVIEW_SECRET`, else HKDF of `FIREBASE_PRIVATE_KEY`, else a fixed key outside production only — changing it orphans stored previews' pictures, not their text), stores a site-relative `/api/link-image?u=&s=` path, and on request verifies the signature in constant time before anything else, sniffs the bytes (SVG, PDF and the rest are refused whatever the header said), decodes with sharp (≤ 30 MP, first frame, `failOn: 'error'`), and remembers every outcome by URL with at most 3 pictures decoding at once (503 beyond a short queue): a picture 10 min, a refusal the address would earn again (blocked, not a picture, too big, unreadable) 5 min, a failure that may pass (timeout, network, DNS, a non-2xx status: `mayPass`) 15 s — and its 404 is `no-store`, so no browser, CDN or app keeps a failure and the next view of the preview gets the picture. A signature stops strangers choosing an address, not a reader asking again and again — hence the memory and the limits.

**Story link previews** (`storyLinks.ts`, `cardLinks.ts`): a paragraph whose only content is one http(s) link — `[t](url)`, `<url>`, a reference link (no picture inside), or plain text that is exactly one `findLinks` match — is a *standalone link*; every other link stays inline. `standaloneLinks(story)` reads the story as CommonMark without GFM, as the apps' parsers do (a bare URL is text there), and leaves out our own hosts (`SITE_HOSTS` + `siteUrl()`'s) and IP addresses, each link once, at most 10; `native/fixtures/story-link-cards.json` pins the rule for the web and both apps (`soleLinks` = what a parser finds, `links` = what the server stores). After publish and apply (never for a draft) `unfurlCardLinks` writes the server-only `linkPreviews` (reading order) and `linkPreviewsFor` (the links they were made for) onto the card: stored entries are reused for links still there, only new links are fetched (3 at a time, one 15 s deadline, through the memory `rememberedPreview` shares with chat; the author's `unfurl` bucket pays per new link, and over it the previews are skipped, never the save), the write re-reads the story in a transaction, removes both fields when no standalone link is left, writes nothing when nothing changed, and never touches `updatedAt`/`excerptAt`. Readers take previews only through `linkPreviewOf`/`linkPreviewsOf` (`previewShape.ts`, client-safe: http(s) and a title required, a picture only from `/api/link-image?`) — chat messages, client `mapCard`, the card page's seed (`PublicCard.linkPreviews`, so `/api/cards/view` too) and v1 `CardDetail.linkPreviews` (anonymous cards too: they name pages, not people). The web reader doesn't re-derive the rule under GFM: `StoryMarkdown` asks `soleLinkParagraphs(source)` which paragraphs (by source offset) are standalone and under which URL, and draws `StoryLinkCard` for one whose URL has a preview (`StoryLinkPreviewsContext`, provided by the card page), the plain link otherwise. A story changed outside publish/apply (older app builds) keeps stale previews harmlessly — a client draws a card only for a link still standing alone — until the next save or `backfill.ts link-previews`.

**Rate limits** (`src/lib/api/rateLimit.ts`): costly or far-reaching endpoints spend a per-user budget (`spend()` in v1 routes, `limited()` elsewhere) kept in server-only `rateLimits/{uid}_{bucket}`; over budget answers 429 `rate_limited`. A new LLM, upload or notify endpoint should take a bucket. `resonate` is 20 a day: picking a card connects, taking it back disconnects, and the pair must not become a way to reach anyone.

API routes authenticate with the `__session` cookie **or** `Authorization: Bearer <Firebase ID token>` (native apps) — both via `getCurrentUser()`.

**`/api/v1` is a contract.** Zod schemas in `src/lib/api/v1/schemas.ts` are the source of truth: routes validate with them (`withUser` + `parse` in `http.ts`, errors always `{ error: { code, message, issues? } }`), and `npm run api:openapi` writes `openapi/v1/openapi.json`, from which the iOS (swift-openapi-generator) and Android (openapi-generator) clients are generated. Within v1 change additively only; clients tolerate unknown fields (no `additionalProperties: false`), and optional request fields accept `null` (Kotlin clients send it, Swift omits it). The services (`service.ts`, `reads.ts`; shapes in `present.ts`) run on the Admin SDK, which bypasses `firestore.rules` — every guarantee the rules give the web client (blocks, quotas, visibility) must be re-checked there and covered in `test/emulator/apiV1*.emulator.test.ts` (`canView` in `present.ts` is `cardVisible`). Every v1 GET answers through `cachedJson(req, body, OWN | BRIEF | NEVER)` (`src/lib/api/v1/cache.ts`): always `private`, never `s-maxage`; ETag + 304; `Vary: Authorization, Cookie, X-Resonance-Cache`. The viewer's own things are `no-cache`; others' cards, profiles and lists may be reused 30 s, and the recommended feed until UTC midnight when `fresh` (`no-store` when `stale`) — but only by clients that send `X-Resonance-Cache: 1` (the current apps, whose caches are per account and re-ask after the viewer's writes); everyone else revalidates. Any server path that makes a card non-public, anonymous or gone revalidates its pages with `revalidateLocalized([...cardPagePaths(card), ...profilePagePaths(handle), ...landingPagePaths(before, after)])` from `src/lib/api/revalidate.ts` (the purge's `PurgeReport.pages` does it for the cron). v1 lists read cards with `LIST_FIELDS` (`summary.ts`) and show their stored `excerpt`/`readMinutes`, falling back to the story when `updatedAt` is later than `excerptAt`: a server write that changes a published card's story spreads `summaryFields(story)`, and one that changes nothing a list shows doesn't bump `updatedAt`. Response enums are a closed contract (normalize with `visibilityOf()`; a new value is a breaking change). Every v1 answer has `Server-Timing` (`auth`, `app`, `cold`); `FIRESTORE_PREFER_REST=1` puts the Admin SDK on REST to compare cold starts. Routes whose parameter is a card id (resonances/related/links, notes' `cardId`, messages' `cardRef`) read by id only (`visibleCardById`); only `GET /cards/{key}` and report resolve slugs (`cardByKey`), before the document read, never beside it. Lists check visibility with `visibleTo()` (one batched connection read per author).

### Safety (App Store 1.2 / 5.1.1(v))

- **Blocking**: `users/{uid}/blocks/{blockedUid}` (owner-only). `blockedBetween()` in the rules refuses connections, messages, invites, notes, notifications and card links across a block, both directions; blocking also deletes the connection. Client reads drop blocked authors in `lib/data/hooks` (`getMyBlockedIds`).
- **Blocks hide people and their named cards, never anonymous cards**: the reader writes their own block list, so any answer about an anonymous card that changed when they blocked someone would name its author (block a guess, ask, unblock, next). Every server read keeps an anonymous card whoever the viewer blocked (`blockHides` in `present.ts`: the card, `?keys=`, feeds, a card's lists, card box shelves); the rules let a resonance draft answer one across a block (`originalReadable`); and what is aimed at one across a block — a note, a resonance, publishing an answer — is accepted and silently not delivered: the note is kept as its writer's own but addressed to no one (`toUserId: null`, no bell, no push) and names whom it was withheld from (`withheldFor`, read by no client, never exported), the resonance points at it and reaches no one. Every path asks the pen name before the blocks; a message's `noteRef` must be a note its recipient left the sender, one error otherwise, and one on the sender's anonymous card is left off the message (as is one gone with its card); the export keeps a note's words, card and date, never whom it reached or whether it was read — every note alike, since any difference between two would be a tell; deleting a published card — the server's alone, the rules let a client delete drafts only — deletes its notes after it; the account purge deletes the notes left on the account's cards just before each card (`byCard` in `collectAccountData`: a purge cut short never strands one) and those on cards gone earlier by `toUserId` or `withheldFor`, so the withheld go with the delivered. A note or resonance bell on an anonymous card says so (`payload.anonymous`) and its push opens the card, never the writer's thread (and so does its row in the web bell — see Push). The recommender lifts an author's cards for a reader who answered them only when the card is named (read as it is now, `namedCardIds`), counts only answers their originals show (published, public, named), and `/api/recommend/feed` answers card ids and reasons, never scores. An anonymous card is public or private, never for connections only: whether a reader could open one would turn on a connection, and a block ends the connection — the card vanishing would name its author. The rules (`anonymousForConnections`) refuse a new draft, an update of a published card's `anonymous`/`visibility` (an unpublished draft may be so, for the builds before letters — publishing refuses it) and a pending edit (`editedAudience`: the edit's visibility, else the card's) that would make one so; publishing, PATCH and edits/apply refuse it with 400 'An anonymous card is public or private.' (`lib/db/firestore/cardContent.ts`); a card already that way stays editable in everything else, is read as private by everyone else (`cardVisible`, the rules' `cardOpen`), and `scripts/integrity.ts` lists the published ones — never migrate them. `test/emulator/anonymousBlocks.emulator.test.ts` asks each probe with and without a block, either way. Named cards keep every block behaviour.
- **Reports**: filed through the server (`POST /api/v1/reports`, `…/cards/{key}/report`), which writes server-only `reportEvidence/{id}` in the same batch; read/resolve with `npm run moderation`. `reports/*` still takes a client create of a person or message report from the tester builds (no evidence then) — make it `create: false` once they're retired.
- **Who can reach whom**: two people message only once connected, and only the server connects them — through a resonance, a card's author answering a note, or an old invite its recipient accepts while it's open. Every path asks a pen name of whoever reaches out (`hasPenName` in `conversations.ts`: a profile with a non-empty `handle`; sending a message too) — before the blocks — and finds no block either way (on an anonymous card a block is never the answer, see above). Picking an anonymous card to resonate with reaches no one, so it needs no pen name. A resonance reaches its original (connection + bell) only when it is published, **public and named** (`reachable` in `resonate.ts`: a private or connections-only one is never listed under the original, an anonymous one would be named by the connection), through one transaction (`readReach` → `reachOriginal`) shared by publish, `POST …/resonances`, PATCH and edits/apply; the bell `notifications/resonance_{uid}_{originalId}` is the record — written once, and while it exists no bell is written and no connection made (between two already connected the resonance is still kept as a reason), so a reader rings a card's author once whichever path fires, and a connection a block ended isn't made again without a ring (an answered note still can). A bell from before the fixed id (`type: 'resonance'` under a random id, same `userId` / `payload.fromUserId` / `payload.cardId`) counts too: `readReach` looks for one with an equality-only query in the transaction while the fixed one is missing (single-field indexes merge; no composite index). Publish waits for the reach (best effort); PATCH and edits/apply run it after the response (`tryReachResonance` through `ringAfter`). An anonymous original rings but connects no one; an existing connection is never written over. For one day (2026-06-04/05, 5998ec4 → 90d9728) a "like" rang the very same row, and only its date tells the two apart (every such row from before 90d9728 went live was a like, but when that was is recorded nowhere), so a reader who liked a card that day counts as having rung its author: a resonance of theirs with it rings and connects no one; `scripts/integrity.ts` lists those rows. Why two people are connected lives in server-only `connectionOrigins/{pair}` (`origins.ts`; never on the connection, which both read, while a resonance can be made anonymous later): `reasons` — each standing resonance that reached, `resonance_{by}_{cardId}` (the one that connected them and each one after it while they were), `answered_{writer}` once the original's author of a standing resonance writes to its writer (a message, or a note in their thread: `answeredBy`, read against the reasons in that words' own transaction, so words from before a resonance never answer it and the resonator's own answer nothing; kept here, not judged from the thread, which either may delete), `letter` once a letter's recipient answered it, `invite_{id}`, and `legacy` for a connection made before reasons were kept (added with its first reason) — and `resonanceCards` to find them by. Only resonances are ever taken back; every other reason stands for good. A new connection writes it afresh (`connect`), so nothing of an earlier one a block ended counts. Taking a resonance back — `DELETE …/resonances/{cardId}`, deleting the card, or hiding it by PATCH or an applied edit (`hiddenResonance`) — removes its reason in the same transaction (`readTakeBack` → `takeBack`; deleting reads the card in that transaction, so a racing resonance can't outlive it), and the connection goes exactly when no reason is left. A connection made before reasons were kept is never taken back (its first reason comes with `legacy`). The bell stays too, so answering that card again rings and connects no one. Open with the owner: an original's author who deletes, hides or anonymizes their card keeps the connection (either of them can end it).
- **Notes are letters** (`sendNote` / `sendMessage` in `conversations.ts`): a note on a named card between two people not connected threads and rings like any note but connects no one; it waits in the conversation's `request` (server-only: the rules let a participant change nothing but their own unread) until its recipient answers — their first message, or a note of theirs back while it waits (crossing letters), connects the two and deletes `request` in the same transaction. Meanwhile its writer can leave 3 notes in all and can't message. The count lives in `letters/{writer}_{recipient}` (`{ from, to, count, at, cardId }`, server-only, closed to clients by the rules), not in the conversation, so either participant may delete the thread: the writer withdraws the letter, the recipient declines it — `request` goes with it, and the recipient's reply connects no one — and neither resets the count. Only its recipient answers a letter: their message or note to its writer, or an invite accepted between them, deletes `request` and both people's `letters/*` (`clearLetters`) — and, connected already, keeps the answered letter as a reason they are. A resonance connecting them leaves the letter as it is (clients ignore `request` while connected), so taking that resonance back leaves the letter and its cap exactly as before; the purge takes `letters/*` from either side. A block either way refuses the answer and leaves the letter as it is; a note on an anonymous card never opens, counts toward or answers one (a cap or a crossing there would tell whose card it is). People old notes connected stay connected.
- **Pen names**: `POST/PATCH /api/v1/me` reserve `handles/{lowercased name}` (server-only, one get allowed) in the profile's transaction and release it on rename; lookups by pen name read the reservation first. A client list of `users` must carry `limit` ≤ 30. A profile without a pen name (made before onboarding asked for one) can reach no one: the web's `AppShell` sends it to `/signup`, and both apps send it to onboarding (as they do on GET /me's 404); either one's POST names it.
- **Account deletion**: `accountDeletions/{uid}` (admin-only) → purged by the cron. A new collection that stores a uid must be added to `collectAccountData()` in `src/lib/account/deletion.ts` (it also takes the pen name's reservation, the person's `uploads/*` pictures, report evidence on either side, `letters/*` and `connectionOrigins/*` either way, their push switches and push logs (`notificationSettings`, `pickPushes`, `connectionCardPushes`), pending edits naming them, notes withheld from them (`withheldFor`), and what is found through one of their cards — legacy resonance records, every note left on it — just before that card). The cron purges two accounts at a time, 16 trees at a time each, through one BulkWriter, starts nothing new past its budget (logged `Account purge: out of time`; the rest waits for the next run) and deletes the profile last. `/api/account/export` streams compact JSON (bucket `export`).

### Story editor & its Markdown

Stories are stored as Markdown, so the editor's schema *is* the storage format. `src/lib/markdown/editorSchema.ts` holds it (nodes + their Markdown serialization, no UI); the web `MarkdownEditor` adds React node views and the native apps' WebView island (`native/editor`) adds DOM ones — both call `storyExtensions()`. `native/fixtures/markdown-corpus.json` pins how each kind of content round-trips (`editorSchema.test.ts`, and the same corpus runs inside both apps). After an intentional schema change: `UPDATE_MARKDOWN_CORPUS=1 npx vitest run src/lib/markdown/editorSchema.test.ts` and review the diff.

### Security headers

`next.config.ts` sends, on every path (`src/lib/api/securityHeaders.ts`): `X-Frame-Options: SAMEORIGIN` + CSP `frame-ancestors 'self'`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy`, and a **report-only** CSP (reports to `/api/csp-report`) listing what the site loads — Firebase Auth's iframe and endpoints, apis.google.com, Turnstile (challenges.cloudflare.com), the R2 image origin (and a former one during a move), fonts. ### App Check (watched, not enforced)

Firestore and Auth are in App Check's monitoring mode, and the API only logs. The web's provider is Cloudflare Turnstile as a custom provider (`src/lib/appCheck/config.ts`, `src/lib/auth/firebase/appCheck.ts`): on the production origin only (`NEXT_PUBLIC_SITE_URL`; previews, local builds and emulators go without), the invisible widget's token is traded at `POST /api/app-check` (Cloudflare siteverify with `TURNSTILE_SECRET_KEY` — host, action, single use — then the Admin SDK mints a 12 h token for the web app; ten exchanges per address per 10 min per instance). Nothing waits on a challenge: a token kept from an earlier visit (`resonance:appcheck-until`) starts App Check at once, else the challenge runs when idle and App Check starts once it has a token. `callApi` sends `X-Firebase-AppCheck` when a token is at hand within 150 ms. Every v1 request's token is checked after the response (`withUser` → `noteAppCheck`): one `[appcheck] <valid|missing|invalid> <platform> <route>` line per kind per 10 min per instance, with a count. The privacy policy names Turnstile (its privacy addendum is required for the invisible widget). A new production domain needs the widget's hostname list in Cloudflare and NEXT_PUBLIC_SITE_URL changed together. The apps attest with App Attest (iOS release) and Play Integrity (Android release; every Play signer's SHA-256 must be in Firebase), the debug provider in debug builds, nothing against the emulators; they send the token at hand on API calls (`AppCheckHeader` in both apps) and never wait for one. Enforce only once the logs show `missing`/`invalid` from old builds and scripts alone.

### Native apps (`apps/`)

The iOS (SwiftUI, `apps/ios`) and Android (Compose) apps are a migration of this site; see `apps/README.md` (one HTTP setup with a `Resonance/<version>` User-Agent; sign-out clears Firestore's local data, notifications and the push memo; notification permission is asked after the first note, message or publish, or when a Settings → 通知 switch is turned on; a failed listener is a retry, not "gone"). They take their design tokens, strings, icons and editor from the web through `npm run apps:generate` — so renaming or removing a key in `src/messages/*.json`, redrawing an icon (absolute M/L/C/Z paths only: `scripts/apps/icons.ts` refuses anything else), or changing `tokens.css`, means regenerating (CI fails on stale output). Both apps keep the signed-in account's last answers on disk (latest feed page, today's picks, Me, the published shelf, the block list) for an instant cold start, and send v1 GETs through a per-account HTTP cache that honours `private` + ETag and re-asks after the viewer's own writes (see apps/README.md). The apps read `src/messages` at runtime as-is, with a small ICU subset (`{name}`, `plural` with `=N`/`one`/`other`/`#`); `scripts/apps/l10n.ts` refuses anything else.

**Builds before letters** (the store builds from 7136d72: version 2.0.0, build ≤ 6 on iOS / ≤ 7 on Android; every later 2.0.0 build is iOS ≥ 7, Android ≥ 8 — keep it so — and no other version is old, whatever its build number) are told apart by their User-Agent (`isPreLetterBuild`, `src/lib/api/v1/clientBuild.ts`; one that doesn't parse is never old) and get, from `src/lib/api/v1/preLetter.ts`: `isConnected: true` on `GET /users/{handle}` while that person's letter waits for the viewer's answer (never to its writer, never across a block — their thread and composer open, and the answer connects the two); a 403 instead of the 409 on a note past the unanswered limit; and that 403's and publish's anonymous-for-connections 400's message in the app's language (they show a server message as is). The rules also let an unpublished draft be anonymous + connections (those builds keep a web draft's audience beside their anonymous switch; publish refuses it). None changes the v1 contract; remove them once those builds are retired.

### AI (`src/lib/ai/`)

Card URLs use English slugs (LLM translates the title, then slugify + handle/numeric-suffix collision handling). `openai.ts` wraps API calls, `tasks.ts` defines the tasks (slug base, tag suggestions, story illustration), `slugify.ts`/`tags.ts` are pure logic with tests. OpenAI is only called from server routes — the key never reaches the client — and every call carries a timeout (`signal`). A route that can reach the OpenAI client runs in `hnd1`: list it in vercel.json `functions` (with its `maxDuration`); `src/lib/ai/regions.test.ts` follows every route's imports and fails on a missing or stale entry. Recommendations (`src/lib/recommend`) search the vector store by COSINE distance (smaller = closer); the light boost for authors the reader has answered (`getEngagedAuthorIds`) counts named originals only — one for an anonymous card's author would point at them.

### Storage & Image Pipeline

`src/lib/storage/` is an abstraction over Cloudflare R2 (S3-compatible API via `@aws-sdk/client-s3`). Keys are `{kind}/{yyyy-mm}/{uuid}.{ext}` (no uid); `storeOwned()` records the owner in server-only `uploads/{uuid}`. Once `config/storage` names the host, the rules take covers and avatars from it only. Images are compressed client-side (`src/lib/images/compress.ts`), uploaded through `/api/upload` or `/api/generate-image`, converted to AVIF with sharp (`src/lib/storage/image.ts`), and served from `R2_PUBLIC_BASE` with `Cache-Control: public, max-age=31536000, immutable` (keys are UUIDs, never rewritten). R2 CORS config is in `r2-cors.json`.

**Moving the storage to a new host** (the r2.dev host → `img.resonance.channel`, an R2 custom domain on the same bucket: both serve every key). Uploads go to `R2_PUBLIC_BASE` only; `R2_FORMER_PUBLIC_BASES` (comma-separated) lists the earlier bases, which everything that recognizes "a picture we stored" also accepts — `storageKeyOf()`/`publicBases()` in `src/lib/storage/publicUrl.ts` (applying an edit, `/api/og` share images, the integrity check) and the report-only CSP's `img-src`/`media-src`. In the rules, `storedFile()` takes `config/storage.host` or any host in its optional `formerHosts`, so a draft or pending edit still holding an old-host cover stays saveable. The order matters, since the rules refuse a cover on a host `config/storage` doesn't name: deploy the rules; with `R2_PUBLIC_BASE` set to the new base and the old one in `R2_FORMER_PUBLIC_BASES`, run `backfill.ts storage-host --apply` (the host it replaces joins `formerHosts`); deploy the site with the same two variables; then `backfill.ts rehost-images --apply` rewrites stored URLs on a former base to the same key on the new one — profile photos, covers and story pictures of cards and pending edits, without touching `updatedAt` or the list summary; `reportEvidence/*` keeps what was reported as it was. Retire an old host only once a `rehost-images` dry run finds nothing left on it: drop it from `R2_FORMER_PUBLIC_BASES` and, by hand, from `formerHosts`.

### Component Hierarchy

Components follow a three-tier atomic structure:

- **`atoms/`** — Primitive visual elements. Many generate procedural SVG shapes (e.g., `HandDrawnBorder`, `OrganiBlob`, `ShapeGrain`) using utilities in `src/lib/design/`.
- **`molecules/`** — Composed components (`StoryCard`, `CardEditor`, `CardDetail`, `EmbedStoryCard`, `Modal`, `Panel`, `PageShell`).
- **`sections/`** — Full page sections (`AppHeader`, `HeroSection`, `CardFeedSection`, …).

When building UI, reuse existing primitives (`OrganicButton`, `Panel`, `Field`, `Icon`, `TagPill`, `PageShell`) instead of inline styles or duplicated SVG.

### Design System

All design tokens are CSS variables in `src/styles/tokens.css`, using the **OKLCH color space**. Fonts: Playfair Display (headings) + DM Sans (body) + Noto Serif/Sans TC, self-hosted with next/font in `src/styles/fonts.ts` (variables --font-playfair, --font-dm-sans, --font-noto-serif-tc, --font-noto-sans-tc on `<html>`, from which tokens.css builds --font-heading / --font-body). Hand-drawn border stroke widths must use the `INK` / `INK_LIGHT` / `INK_STRONG` "one pen" tokens from `src/lib/design/strokes.ts` — never hardcode `strokeWidth`. A runtime `TweaksPanel` provider (`src/components/providers/TweaksPanel.tsx`) exposes accent color, heading font and grain as live CSS variable overrides — useful for design iteration. A hover wash on a hand-drawn surface is `<BrushWash>` (atoms/BrushWash: a transform-grown disc clipped to the shape's own outline) — never an animated SVG mask radius over filtered shapes. `HandDrawnBorder` memoizes its path by value (inline `segmentsH={[3, 4]}` is fine); a shape repeated many times with a few chalk seeds uses `sharedChalk` and one `<ChalkFilters seeds>` per page, as the thought map does (whose world is memoized apart from its camera: keep camera values out of it). Server HTML is the finished page: a shape not yet measured shows its CSS stand-in (`.res-shape-stand-in`, `data-shape-pending`), and both phone and desktop chromes render with CSS choosing one. A chat bubble is `lib/design/bubble` — the apps' recipe to the point (`seedFromId`, corners tucked in a run) — worn as a `clip-path` once measured, so what it carries (a link's picture, a shared card's cover) runs edge to edge and ends at its wobble; the thread's rows are memoized (`MessageRow`, actions from `ThreadActionsContext`) and its draft lives in `ThreadComposer`, so typing never draws the thread again. A menu whose trigger sits in something that scrolls floats (`OrganicMenu` `floating`); a glyph-only tool is `BareIconButton`. A modal draws no ✕ (`Modal`): the backdrop and Escape close it, a named close stays for screen readers, and one with nothing else at its foot (a list, a picker) takes `closeButton`. A page's own back + title bar is `HeaderBar` (the app header's `HeaderChrome`): a phone's settings detail, and the writer at every width, whose back asks before leaving written work (`CardEditor`'s ref: `hasWork`, `saveNow` — the apps' rule).

### Organic/Procedural SVG

The visual identity relies on hand-drawn aesthetics generated at runtime:

- `src/lib/design/wobRect.ts` — wobbly rounded rectangles via seeded bezier curves
- `src/lib/design/prng.ts` — seeded PRNG for deterministic per-element randomness
- `src/lib/design/wavyPath.ts` — wavy SVG path generation (plus `wobCircle.ts`)

Shapes use a `seed` prop so they render consistently across SSR and client hydration.

## Testing

Tests run on **Vitest** + **@testing-library/react** + **jsdom**. Config is `vitest.config.ts`; shared setup is in `test/`. We write **integration-style unit tests** — exercise a whole feature (an adapter's rules, a hook's composition, a component's interaction), not single trivial functions. No E2E.

### Where tests live

- **Co-locate** unit/component tests next to their source: `Foo.tsx` → `Foo.test.tsx`, `foo.ts` → `foo.test.ts`. This is the default.
- **`test/`** holds only shared infra, not test cases:
  - `test/setup.ts` – global setup (jest-dom matchers, `afterEach` cleanup, jsdom `ResizeObserver`/`matchMedia` stubs that organic atoms need via `useElementSize`/`useIsMobile`).
  - `test/fakeAdminDb.ts` – an in-memory Admin Firestore with a `reads` log, for rendering server pages and routes without the emulator.
  - `test/render.tsx` – `renderWithIntl()` wraps a component in `NextIntlClientProvider` (loads real `en` messages so assertions hit real copy); also re-exports the Testing Library surface + `userEvent`.

### Environment & the jsdom directive

Default env is **node** (fast – suits pure-logic suites). Any test that renders React must opt into jsdom with a top-of-file directive:

```ts
// @vitest-environment jsdom
```

`tsconfig.json` uses `jsx: "preserve"` for Next, so the Vitest config sets `esbuild.jsx: 'automatic'` – test files don't import React. `vitest.config.ts` is excluded from `npm run typecheck` (build tooling, dual-Vite type noise).

### Conventions

- **Mock at the module boundary**, not internals. Hooks/components that touch Firebase mock the read/write layer (`@/lib/db/firestore/client/*`), `useAuth`, and navigation (`@/i18n/navigation`) with `vi.mock`. Pure-logic suites (adapters, mappers, design utils) mock nothing.
- **SWR hooks**: render via `renderHook` wrapped in `<SWRConfig value={{ provider: () => new Map(), dedupingInterval: 0 }}>` so each test gets an isolated cache; `await waitFor(() => expect(result.current.data).toBeDefined())`. To test focus behaviour use `{ ...SWR_DEFAULTS, provider, dedupingInterval: 0, focusThrottleInterval: 0 }` (SWR ignores focus for 5 s after mount). When a hook returns the raw SWR object, read `.data` during render (`renderHook(() => useX().data)`) — SWR only re-renders for fields a render read. A component rendering CardLinkGrid needs `useAuth` mocked (the prefill reads the viewer).
- **Query by role / label / text**, asserting the behavior a user sees – avoid implementation details.
- **Component gotchas**: for a control gated by a `pointer-events: none` wrapper, use `userEvent.setup({ pointerEventsCheck: 0 })` to test the component's own validity gate. For long text input, prefer `fireEvent.change` over `userEvent.type`. Await async effects (e.g. a `useEffect` data load) before a test ends to avoid `act()` warnings.
- **Determinism**: seeded design utils (`prng`, `wobRect`, `wavyPath`) are tested for same-seed stability – this is what guarantees SSR/CSR hydration parity.

### Verification (hard rules)

These are non-negotiable — both rules exist because their violation has already shipped regressions:

- **UI changes**: before calling the work done, verify in the browser preview at **both desktop and mobile** widths (`preview_resize`). Mobile-only fixes have silently broken the desktop layout before (and vice versa), and a fix to one organic component must be checked against its siblings (buttons, inputs, selects, toggles share the same border language).
- **Data-layer changes** (repositories, `client/*` read-write modules, adapters, page data fetching): ship with an integration-style test that fails without the change. A Server-Render→Firestore migration once broke the home feed and card pages while the whole suite stayed green.
